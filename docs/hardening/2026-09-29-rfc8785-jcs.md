# Kanonikalisasi JSON RFC 8785 (JCS) untuk Payload Tanda Tangan Ruleset

Tanggal: 2026-09-29
Branch: `hardening/rfc8785-jcs-canonicalization`
Basis: `main` @ `9e2a044` (PR #14 belum di-merge; branch ini tidak menimpanya)

## 1. Masalah yang ditutup

Sebelum perubahan ini, verifier menerima **teks berkas apa adanya** sebagai
payload tanda tangan. Akibatnya:

- ruleset yang **setara secara semantik** tetapi berbeda format (urutan kunci,
  spasi, escape) menghasilkan tanda tangan berbeda;
- **penyuntingan kosmetik** — mis. `{"a":1,"b":2}` ditulis ulang menjadi
  `{ "b": 2, "a": 1 }` — membatalkan tanda tangan yang sah.

Ini membuat rilis bertanda tangan rapuh: setiap alat yang memformat ulang JSON
(editor, linter, `jq`) akan mematahkan rantai kepercayaan.

### Aturan kanonikalisasi yang diterapkan

1. Blok `signature` tingkat atas **dikeluarkan** dari payload (tanda tangan tidak
   dapat dihitung atas dirinya sendiri).
2. Kunci objek diurutkan menurut **code unit UTF-16** (RFC 8785 §3.2.3) — bukan
   menurut byte UTF-8, yang memberi urutan berbeda untuk non-ASCII.
3. Ruang kosong antar token dibuang; string di-escape menurut ECMAScript
   (`\b \t \n \f \r \" \\`, kontrol lain sebagai `\u00xx` huruf kecil).
4. Angka diserialkan dalam bentuk **terpendek yang bolak-balik tepat**
   (RFC 8785 §3.2.2.3).
5. Urutan elemen array **tidak** diubah.

### Gagal-tertutup

JSON tidak sah, kunci duplikat, angka `NaN`/`Infinity`/overflow, dan UTF-8 tidak
sah (overlong, surrogate, di luar U+10FFFF) semuanya menghasilkan `ok=false`.
`nq_ruleset.cpp` memperlakukan kegagalan itu sebagai `kSignatureInvalid` —
ruleset **ditolak**, bukan diterima tanpa verifikasi.

## 3. Dua bug nyata yang ditemukan saat pengujian

Keduanya ditemukan oleh uji, bukan oleh penalaran — dan keduanya akan
menghasilkan tanda tangan yang **tidak kanonik** bila lolos.

### Bug 1 — `std::to_chars` mode general tidak memberi bentuk terpendek

Pada libstdc++ GCC 12, `std::to_chars(buf, end, v)` (mode general) menuliskan
nilai **eksak** untuk bilangan bulat besar:

```
295147905179352830000  ->  to_chars general = 295147905179352825856   (SALAH)
                            to_chars scientific = 2.9514790517935283e+20 (BENAR)
```

RFC 8785 mewajibkan bentuk terpendek, jadi mode general **tidak dapat dipakai**.
Perbaikan: pakai `std::chars_format::scientific`, lalu susun ulang menurut aturan
penempatan titik desimal ECMAScript. Ditambah jaring pengaman: hasilnya wajib
`strtod` bolak-balik ke `double` yang sama, jika tidak → gagal-tertutup.

### Bug 2 — `out->assign` menimpa buffer alih-alih menambah

Pada ekor `SerializeNumber`, `out->assign(...)` menimpa seluruh isi keluaran
yang sudah dibangun, sehingga `[3,1,2]` menjadi `2` dan `{"b":1,"a":2}` menjadi
`2`. Perbaikan: `out->append(...)`.

Kedua bug ini **tidak akan terlihat** tanpa uji vektor resmi — inilah alasan
vektor RFC 8785 diuji persis, bukan sekadar "bentuknya kelihatan benar".

## 5. Yang masih belum

- **Jalur pembangkitan tanda tangan** (signing) di luar biner aplikasi belum ada,
  beserta prosedur penyimpanan kunci privat. Tanpa ini, ruleset produksi belum
  dapat ditandatangani dengan aman.
- **Ruleset produksi bertanda tangan belum pernah diverifikasi end-to-end.**
  Yang diuji adalah vektor RFC 8032 dan payload sintetis, bukan ruleset nyata
  bertanda tangan.
- **Uji jalur positif lewat `Ed25519RulesetVerifier::Verify()`** (verifier
  konkret, bukan `Ed25519Verify()` langsung) belum ada — lihat temuan pada
  tinjauan PR #14.
- **Workflow CI belum pernah dijalankan di GitHub Actions**; yang terbukti
  adalah YAML sah + langkah-langkahnya dijalankan manual di sandbox.
